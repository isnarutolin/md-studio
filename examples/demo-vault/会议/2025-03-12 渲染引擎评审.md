# 2025-03-12 渲染引擎评审

[← 索引](../README.md)

## 结论

**方案定了：Lezer + Decoration，不做富文本模型。**

理由：富文本编辑器把文档存成 AST，导出 Markdown 时重新序列化，用户手写的格式细节必然丢失——空行、对齐、`*` 还是 `-`、缩进宽度。文件要进 Git、要被别的工具打开，字节级保真不可让步。

## 性能记录

| 文档规模 | 按键延迟 | 结论 |
| :--- | ---: | :--- |
| 100 行 | < 1 ms | 无感 |
| 2000 行 | 3.1 ms | 无感 |
| 6000 行 + 1000 表格 | 2.0 ms | 无感 |
| 8500 行 + 500 代码块 | 5.1 ms | 可接受 |

> 关键优化：不要下钻遍历代码块内部的嵌套语法树。一个 JS 代码块几百个节点，每次按键白花 8.8ms。

## 遗留问题

1. 块装饰全量重建太浪费 —— 改成"没碰到含 `|` 的行就 `map(changes)` 平移"
2. 每次光标移动都重建 —— 用 `revealKey` 比对，没变就复用
3. 模糊搜索连续加分跨间隔累加 —— `2025` 会把 `2024` 排前面
